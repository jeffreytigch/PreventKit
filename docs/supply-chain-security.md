# Supply Chain Security

This document describes the supply chain security posture of the PreventKit module and guidance for secure deployment.

## External Dependencies

PreventKit has minimal external dependencies by design:

| Dependency | Type | Risk Level | Mitigation |
|------------|------|------------|------------|
| PowerShell 7+ | Runtime | Low | Microsoft-signed, built-in |
| ExchangeOnlineManagement | Module (TABL) | Low | Microsoft first-party, signed |
| Azure CLI (`az`) | Binary (CNI auto) | Medium | Verify signature, pin version |
| Microsoft Defender API | Service | Low | Microsoft first-party, TLS 1.2+ |

## Module Integrity

### No External Module Dependencies

The `PreventKit.psd1` manifest declares **zero** `RequiredModules`. All functionality is self-contained within the module. This eliminates the risk of transitive dependency compromise from the PowerShell Gallery.

### No Code Download/Execution

The module never:
- Downloads and executes scripts (`Invoke-Expression`, `iex`)
- Downloads files for execution (`Invoke-WebRequest` + `Invoke-Expression`)
- Installs modules at runtime (`Install-Module`)
- Loads assemblies from untrusted paths

### Catalogue Sources

Catalogue sources are user-controlled:
- Local files: No supply chain risk
- HTTPS URLs: User must trust the source; module validates TLS certificates

**Recommendation**: Host catalogue sources in your own version-controlled repository (GitHub, Azure DevOps, etc.) and reference local paths in catalogue declarations.

## Verification Steps

### 1. Verify Module Signature

```powershell
# Check if module is signed
Get-AuthenticodeSignature -FilePath ./src/PreventKit/PreventKit.psd1
```

### 2. Verify File Integrity

```powershell
# Generate SHA-256 hashes of all module files
Get-ChildItem ./src/PreventKit -Recurse -File | ForEach-Object {
    $hash = Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256
    "$($hash.Hash)  $($_.FullName)"
}
```

Store these hashes in your secure deployment pipeline and verify on each deployment.

### 3. Pin Azure CLI Version

In your deployment pipeline, pin the Azure CLI version:

```yaml
# Azure Pipelines example
- task: AzureCLI@2
  inputs:
    azureSubscription: 'your-subscription'
    scriptType: 'bash'
    scriptLocation: 'inlineScript'
    inlineScript: |
      az version
      # Pin to specific version if needed
      # az upgrade --version 2.53.0
```

### 4. Restrict Network Access

Egress destinations depend on which enforcement targets a Run reconciles. PreventKit's
own code contacts the CNI APIs and catalogue sources directly. TABL connectivity, by
contrast, is performed by the first-party `ExchangeOnlineManagement` module when you run
`Connect-ExchangeOnline`, so those Exchange Online endpoints do **not** appear in
PreventKit's source and must be allowed separately.

**CNI path** (`-Target Cni`):

| Destination | Purpose | Ports |
|-------------|---------|-------|
| `api.security.microsoft.com` | CNI API (import, read, batch delete) | TCP 443 |
| `api.securitycenter.microsoft.com` | Token resource / audience | TCP 443 |
| `login.microsoftonline.com`, `login.windows.net`, `*.auth.microsoft.com` | Microsoft Entra ID token endpoint | TCP 443 |
| `169.254.169.254` | Azure Instance Metadata Service (managed identity flow only) | TCP 80 |

When a token is acquired via the Azure CLI, the CLI's own authentication endpoints must
also be reachable.

**TABL path** (`-Target Tabl`) — generated by `ExchangeOnlineManagement`, not PreventKit:

| Destination | Purpose | Ports |
|-------------|---------|-------|
| `outlook.office365.com`, `outlook.office.com`, `outlook.cloud.microsoft` | Exchange Online REST endpoint | TCP 443, 80 |
| `*.outlook.com`, `autodiscover.<tenant>.onmicrosoft.com` | Autodiscover / discovery | TCP 443, 80 |
| `login.microsoftonline.com`, `login.windows.net`, `*.auth.microsoft.com` | Modern authentication | TCP 443 |

TCP port 80 must be open as well as 443; Exchange Online PowerShell connectivity fails
with only 443 allowed.

**Catalogue sources**:

- User-specified catalogue HTTPS URLs (for example `https://lolrmm.io/api/rmm_domains.csv`)

Configure egress firewall rules to allow only the destinations for the targets you
enable. Sovereign clouds (Microsoft 365 GCC High, DoD, Germany, 21Vianet) use different
hostnames for both authentication and Exchange Online; see the environment table in
*Connect to Exchange Online PowerShell* below.

> **This list is not exhaustive.** Microsoft publishes and revises network endpoint data
> monthly. Treat the values above as a starting point and reconcile them against
> Microsoft's live endpoint data:
>
> - [Microsoft 365 URLs and IP address ranges](https://learn.microsoft.com/microsoft-365/enterprise/urls-and-ip-address-ranges?view=o365-worldwide) — see the **Exchange Online** and **Microsoft 365 Common and Office Online** sections.
> - [Microsoft 365 IP Address and URL web service](https://learn.microsoft.com/microsoft-365/enterprise/microsoft-365-ip-web-service?view=o365-worldwide) — machine-readable endpoint feed for keeping firewall rules current.
> - [Connect to Exchange Online PowerShell](https://learn.microsoft.com/powershell/exchange/connect-to-exchange-online-powershell?view=exchange-ps) — TCP port and environment requirements.

## Threat Model

| Threat | Likelihood | Impact | Mitigation |
|--------|------------|--------|------------|
| Compromised Azure CLI | Low | High | Pin version, verify signature, use managed identity instead |
| Compromised catalogue source | Medium | High | Host in private repo, validate content hashes |
| Module tampering in transit | Low | High | Verify hashes, use signed modules, deploy via pipeline |
| Malicious catalogue declaration | Low | Medium | Review declarations in PR, validate adapter allowlist |
| Dependency confusion | None | N/A | No external module dependencies |

## Reporting Security Issues

Report security vulnerabilities privately to the maintainers. Do not open public issues for security concerns.
